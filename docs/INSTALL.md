# คู่มือติดตั้ง GO HR ที่เซิร์ฟเวอร์ลูกค้า

ใช้เวลาประมาณ 20–30 นาที (ส่วนใหญ่คือดาวน์โหลด Docker image)

## 1. เตรียมเครื่อง
- Ubuntu Server 22.04 / 24.04 (VM หรือเครื่องจริง) — แนะนำ 4 vCPU, 8 GB RAM, ดิสก์ 100 GB (รองรับ ~500 คน)
- ติดตั้ง Docker Engine + Docker Compose v2, git, openssl, curl, cron
  ```bash
  curl -fsSL https://get.docker.com | sudo sh
  sudo apt-get install -y git openssl curl cron
  ```
- ชื่อโดเมนหรือ IP ที่พนักงานใช้เข้าระบบ
  - **มีโดเมนสาธารณะ** (เช่น `hr.customer.co.th` ชี้มาที่เครื่องนี้ และเปิดพอร์ต 80/443) → ได้ใบรับรอง HTTPS ฟรีอัตโนมัติ (Let's Encrypt)
  - **ใช้ภายในเท่านั้น (LAN)** → ใช้ `--tls internal` ระบบจะออกใบรับรองเอง (มือถือต้องติดตั้งใบรับรองหรือกดยอมรับครั้งแรก)
  > ต้องเป็น HTTPS เสมอ เพราะมือถือจะไม่อนุญาตให้ใช้ GPS/กล้องบนเว็บที่ไม่ใช่ HTTPS

## 2. ติดตั้ง
```bash
sudo git clone https://github.com/brambroza/go-hr.git /opt/gohr
cd /opt/gohr
sudo deploy/install.sh \
  --domain hr.customer.co.th \
  --tls it@customer.co.th \
  --admin-email it@customer.co.th \
  --company "บริษัท ลูกค้า จำกัด" \
  --license "<license key ที่ออกให้ลูกค้า>"
```
ตัวติดตั้งจะ
1. ดาวน์โหลด Supabase (ฐานข้อมูล PostgreSQL + Auth + Storage) และสร้างรหัสผ่าน/คีย์แบบสุ่มทั้งหมด
2. สร้างตารางและข้อมูลตั้งต้น (ประเภทการลาตามกฎหมาย, ประเภทเอกสาร 14 แบบ, รายการเงินได้/เงินหัก, อัตราภาษี/ประกันสังคม 2569)
3. Build และเริ่มระบบ GO HR + ตัวตั้งเวลางานอัตโนมัติ + Caddy (HTTPS)
4. ตั้งเขตเวลาฐานข้อมูลเป็น Asia/Bangkok และตั้งเวลาสำรองข้อมูลทุกคืน 01:30 (`/etc/cron.d/gohr-backup`)
5. สร้างผู้ดูแลระบบและแสดงรหัสผ่านชั่วคราว (ต้องเปลี่ยนเมื่อเข้าครั้งแรก)

ไฟล์ความลับอยู่ที่ `deploy/.env` และ `deploy/supabase/.env` (สิทธิ์ 600) — รวมอยู่ในข้อมูลสำรองทุกคืน (`config-<เวลา>.tgz`)

รัน `install.sh` ซ้ำได้: คีย์/รหัสผ่านเดิม โดเมน และโหมด TLS ถูกเก็บไว้ (ไม่ต้องใส่ `--domain` / `--tls` อีก) —
ตัวติดตั้งจะ **หยุด** ถ้าพบฐานข้อมูลเดิมแต่ไม่มี `deploy/supabase/.env` เพราะการสร้างคีย์ใหม่จะทำให้เข้าฐานข้อมูลเดิมไม่ได้

ตรวจว่าระบบพร้อม: `https://<โดเมน>/api/public/health` ต้องตอบ `{"ok":true,"db":true}` (ใช้ URL นี้กับ UptimeRobot ได้)

## 3. ตั้งค่าหลังติดตั้ง (ทำผ่านหน้าเว็บ)
1. ตั้งค่า → ข้อมูลบริษัท: โลโก้ เลขผู้เสียภาษี ที่อยู่
2. องค์กร → สาขา (เลขสาขาภาษี / เลขบัญชีนายจ้าง สปส.), โครงสร้างองค์กร, ตำแหน่ง
3. เวลาทำงาน → กะการทำงาน, วันหยุดประจำปี, พื้นที่ลงเวลา (GPS / ช่วง IP Wi-Fi / QR)
4. พนักงาน → นำเข้าพนักงาน (ดาวน์โหลดแม่แบบ CSV), แล้ว ตั้งค่า → ผู้ใช้งาน → "สร้างบัญชีให้พนักงานที่ยังไม่มีบัญชี"
5. เอกสาร → โควต้าการลา → "สร้างโควต้าประจำปี"
6. ตั้งค่า → ตั้งค่าเวลา/เงินเดือน/ภาษี (ตัวหารรายวัน, การหักสาย, บัญชีธนาคารบริษัทสำหรับไฟล์โอนเงิน)
7. (ถ้าใช้ LINE) ตั้งค่า → Automation และแจ้งเตือน → ใส่ Channel access token / Channel secret ของ LINE OA
   และตั้ง Webhook URL ใน LINE Developers เป็น `https://<โดเมน>/api/line/webhook`
   แนะนำสร้าง Rich Menu ลิงก์ "ลงเวลา" → `https://<โดเมน>/m/checkin`, "ยื่นลา" → `https://<โดเมน>/m/requests/new`
8. ย้ายข้อมูลจากระบบเดิม (ระบบ HR เดิมหรือ Excel): ทำตามหน้า **ตั้งค่า → ย้ายข้อมูลเข้าระบบ** ทีละขั้น (9 ขั้น ระบบติ๊กให้เองเมื่อมีข้อมูล)
   - รายชื่อพนักงาน + เงินเดือน + บัญชีธนาคาร → "นำเข้าพนักงาน" (CSV)
   - ยอดสะสมต้นปี (เงินได้ / ภาษี / ประกันสังคม / กองทุน) → ปุ่ม "นำเข้ายอดสะสม" (ข้ามได้ถ้าเริ่มใช้เดือนมกราคม)
   - วันลาคงเหลือ (สิทธิ์ทั้งปี / ยกมา / ใช้ไปแล้ว) → ปุ่ม "นำเข้าวันลา"
   - ทดลองคำนวณเงินเดือนคู่ขนาน 1 งวด เทียบกับระบบเดิมก่อนใช้งานจริง
9. ใส่ช่องทางติดต่อทีมดูแลระบบ (LINE OA / โทร / อีเมล) ที่หน้า **ช่วยเหลือ → แก้ไขช่องทางติดต่อ**

## 4. เครื่องสแกนลายนิ้วมือ / ใบหน้า
- ส่งข้อมูลเข้าระบบอัตโนมัติ: เพิ่มอุปกรณ์ที่ เวลาทำงาน → อุปกรณ์ลงเวลา เพื่อรับ API key แล้วให้ตัวกลาง (middleware) ของเครื่อง POST ไปที่
  `https://<โดเมน>/api/device/push` header `x-device-key: <api key>` body `{"logs":[{"user_id":"123","time":"2026-10-07 08:01:22"}]}`
- หรือดาวน์โหลดไฟล์จากเครื่อง (ZKTeco attlog .dat / CSV) แล้วนำเข้าที่ เวลาทำงาน → นำเข้าเวลา
- Kiosk: เปิด `https://<โดเมน>/kiosk?key=<api key ของอุปกรณ์ชนิด kiosk>` บนแท็บเล็ตหน้าทางเข้า พนักงานสแกน QR ด้วยมือถือ

## 5. งานประจำของผู้ดูแลระบบ
### 5.1 สำรองข้อมูล
- ตัวติดตั้งตั้งเวลาให้แล้ว: ทุกคืน 01:30 → `/var/backups/gohr` (เก็บ 30 วัน) log ที่ `/var/log/gohr-backup.log`
  ตรวจว่าสำรองล่าสุดเมื่อไร: `cat /var/backups/gohr/last-ok.json` · สั่งเองทันที: `sudo deploy/backup.sh`
- ข้อมูลสำรอง 1 ชุด = ไฟล์ที่มีเวลาเดียวกัน

  | ไฟล์ | เนื้อหา |
  |---|---|
  | `db-<เวลา>.dump` | ฐานข้อมูลทั้งหมด |
  | `files-<เวลา>.tgz` | ไฟล์แนบ (เอกสาร รูป ลายเซ็น) |
  | `config-<เวลา>.tgz` | `deploy/.env`, `deploy/supabase/.env`, `deploy/backup.env` — **ความลับทั้งหมดของเครื่องนี้** |
  | `SHA256SUMS-<เวลา>` | ค่าตรวจสอบไฟล์ |

- **ต้องทำก่อนส่งมอบ** (แก้ที่ `deploy/backup.env`):
  1. `BACKUP_OFFSITE` — สำเนานอกเครื่อง เช่น `rclone:<remote>:<path>` (S3 / Google Drive / OneDrive), `user@nas:/path`
     (rsync ผ่าน SSH) หรือดิสก์ที่ mount ไว้ สำเนาบนดิสก์เดียวกันไม่ถือว่าเป็นการสำรองข้อมูล
  2. `BACKUP_PASSPHRASE_FILE` — เข้ารหัสก่อนส่งออก สร้างด้วย
     `openssl rand -base64 48 > /root/gohr-backup.pass && chmod 600 /root/gohr-backup.pass`
     ถ้าไม่ตั้ง ไฟล์ `config-...` จะไม่ถูกส่งออกนอกเครื่อง (เพราะมีความลับ) → เครื่องพังแล้วต้องติดตั้งใหม่ด้วยคีย์ใหม่
  3. **เก็บรหัสผ่านสำรองข้อมูล 2 ที่นอกเครื่องนี้**: ผู้รับผิดชอบไอทีของลูกค้า 1 ชุด + คลังรหัสผ่านของ GoAlong 1 ชุด
     และเขียนที่เก็บไว้ในเอกสารส่งมอบ ไฟล์รหัสผ่านไม่อยู่ในข้อมูลสำรอง — หายแล้วไม่มีใครกู้ข้อมูลได้
  4. ซ้อมกู้คืน 1 ครั้ง (ข้อถัดไป) แล้วบันทึกผลในเอกสารส่งมอบ
- แจ้งเตือนเมื่อสำรองล้มเหลว: ตั้ง `BACKUP_NOTIFY_URL`

### 5.2 กู้คืน
- **ซ้อมกู้คืน** (ไม่กระทบข้อมูลจริง แอปทำงานต่อได้): `sudo deploy/restore.sh --drill /var/backups/gohr/db-YYYYMMDD-HHMM.dump[.enc]`
  ระบบกู้คืนลงฐานข้อมูลชั่วคราวแล้วแสดงจำนวนแถวเทียบกับฐานจริง — ทำก่อนส่งมอบและทุกครั้งที่เปลี่ยนการตั้งค่าสำรองข้อมูล
- **กู้คืนจริง**: `sudo deploy/restore.sh --restore <db-...dump[.enc]> [<files-...tgz[.enc]>]` ต้องพิมพ์ `RESTORE` ยืนยัน
  1. ตรวจ checksum / ถอดรหัส / อ่าน dump ให้ผ่านก่อนแตะข้อมูลจริง
  2. สำรองฐานข้อมูลปัจจุบันไว้ที่ `pre-restore-<เวลา>.dump`
  3. หยุดแอป → แทนที่ข้อมูลของ GO HR (ตาราง ผู้ใช้ ระเบียนไฟล์แนบ) ในธุรกรรมเดียว — ผิดพลาดตรงไหนข้อมูลเดิมยังอยู่ครบ
  4. รัน `migrate.sh` (กรณีข้อมูลสำรองมาจากเวอร์ชันเก่ากว่า) → เปิดแอป

  ข้อมูลที่บันทึกหลังเวลาสำรองจะหายทั้งหมด
- **เครื่องพัง ย้ายไปเครื่องใหม่**
  1. เตรียมเครื่องตามข้อ 1 แล้ว `git clone` เวอร์ชันเดียวกับเครื่องเดิม
  2. นำไฟล์สำรอง (`db-`, `files-`, `config-`, `SHA256SUMS-`) และไฟล์รหัสผ่านมาวางบนเครื่องใหม่
  3. แตกไฟล์ตั้งค่า (โฟลเดอร์ปลายทางต้องว่าง):
     `sudo mkdir -m 700 /root/gohr-config && sudo BACKUP_PASSPHRASE_FILE=/root/gohr-backup.pass deploy/restore.sh --config <config-...tgz[.enc]> /root/gohr-config`
     แล้วคัดลอก `.env` → `deploy/.env`, `supabase/.env` → `deploy/supabase/.env`, `backup.env` → `deploy/backup.env`
  4. `sudo deploy/install.sh` (ไม่ต้องใส่ตัวเลือก — ใช้โดเมน/TLS/คีย์จากไฟล์ที่คัดลอกมา ห้ามใส่ `--admin-email`)
  5. `sudo deploy/restore.sh --restore <db-...> <files-...>` แล้วเข้าระบบตรวจข้อมูล

### 5.3 อัปเกรดเวอร์ชัน
```bash
cd /opt/gohr && sudo deploy/upgrade.sh            # เวอร์ชันล่าสุดของ branch ปัจจุบัน
sudo deploy/upgrade.sh --ref v1.3.0               # ระบุ tag / commit
```
ลำดับ: สำรองข้อมูล → ดึงโค้ด → build (เวอร์ชันเดิมยังให้บริการ) → หยุดแอป → ปรับฐานข้อมูล → เปิดเวอร์ชันใหม่ → ตรวจ `/api/public/health`
- ไม่สร้างคีย์ใหม่ ไม่เปลี่ยนโดเมนและโหมด TLS ที่เลือกตอนติดตั้ง
- หยุดทันทีถ้าสำรองข้อมูลไม่สำเร็จ หรือมีไฟล์ของระบบถูกแก้บนเครื่อง
- ถ้าเวอร์ชันใหม่ไม่ขึ้น สคริปต์จะแสดงวิธีกลับ (commit เดิม, image เดิม, ข้อมูลสำรองก่อนอัปเกรด)
  การปรับฐานข้อมูลเดินหน้าอย่างเดียว — กลับไปโค้ดเดิมหลังปรับฐานข้อมูลแล้วต้องกู้คืนข้อมูลสำรองชุดนั้น
- **อย่า**ใช้ `install.sh` เพื่ออัปเกรด และ**อย่า**ลบไฟล์ใน `deploy/supabase/`

### 5.4 อื่น ๆ
- เวอร์ชันของ Supabase / Caddy ล็อกไว้ใน `deploy/versions.env` การอัปเกรด Supabase ต้องตั้งใจทำ:
  ทดสอบบน staging → `sudo deploy/backup.sh` → `sudo deploy/install.sh --upgrade-supabase`
  (ดึงชุด docker ของ Supabase ตาม `SUPABASE_REF` ใหม่ คีย์และข้อมูลเดิมคงอยู่)
- เขตเวลาฐานข้อมูลตั้งเป็น Asia/Bangkok โดย `migrate.sh` (วันที่ "วันนี้" ของวันลา ทดลองงาน งวดเงินเดือน ต้องเป็นเวลาไทย)
- Content-Security-Policy เริ่มแบบ **รายงานอย่างเดียว** (ไม่บล็อก) ดูรายงานได้จาก `docker compose logs app | grep csp-report`
  เมื่อใช้งานจริง 2 สัปดาห์แล้วไม่มีรายงานผิดปกติ ให้ตั้ง `CSP_ENFORCE=1` ใน `deploy/.env` แล้ว `docker compose up -d`
  (ถ้าต้องโหลดสคริปต์/รูปจากโดเมนอื่น เช่น LINE LIFF ให้ใส่ `CSP_EXTRA_ORIGINS=https://host1,https://host2`)
- ดูสถานะ: `cd /opt/gohr/deploy && docker compose ps` · ดู log: `docker compose logs -f app`
- อย่าเปิดพอร์ต 8000 (Supabase Studio) และ 5432 สู่อินเทอร์เน็ต — เปิดเฉพาะ 80/443
